Network Protocols — Lesson 04

DNS — How Names Become Addresses

From api.example.com to 93.184.216.34, and the pitfalls hiding in node:dns.

The Problem DNS Solves

Computers communicate using IP addresses (93.184.216.34). Humans use names (api.example.com). DNS — the Domain Name System — is the internet's phone book: it maps names to addresses.

Every time your Node.js server connects to a database at db.internal, calls a third-party API at api.stripe.com, or sends email through smtp.sendgrid.net, DNS is running under the hood.

The DNS Resolution Chain

What actually happens when you call fetch('https://api.example.com/users'): 

1. Browser/OS checks local cache
   → Found? Use it (skip the rest)

2. OS checks /etc/hosts (or Windows hosts file)
   → Found? Use it (great for local dev overrides)

3. Query your configured DNS resolver
   → Usually your router (192.168.1.1) or 8.8.8.8 (Google) or 1.1.1.1 (Cloudflare)
   → Resolver checks its own cache

4. Resolver queries the root nameservers (13 of them, globally distributed)
   → "Who handles .com?"

5. Root says: "Ask the .com TLD nameserver"
   → "Who handles example.com?"

6. TLD says: "Ask ns1.example.com (the authoritative nameserver)"
   → "What is api.example.com?"

7. Authoritative server returns: api.example.com → 93.184.216.34, TTL=300

8. Result is cached (at resolver + OS + app) for TTL seconds

This whole chain typically completes in 20–150ms on the first query. Subsequent queries hit the cache and take <1ms.

TTL (Time-To-Live) is the number of seconds DNS clients should cache the answer. A TTL of 300 = 5 minutes. Short TTLs enable fast failovers (useful during incidents). Long TTLs reduce DNS load and speed up lookups. Most production APIs use 60–300s.

DNS Record Types You'll Actually Encounter

RecordMapsExampleUse case
A hostname → IPv4 api.example.com → 93.184.216.34 The most common — where your server lives
AAAA hostname → IPv6 api.example.com → 2606:2800:220:1:: IPv6 equivalent of A
CNAME hostname → hostname www.example.com → example.com Aliases — redirecting one name to another
MX domain → mail servers example.com → mail1.example.com Email delivery routing
TXT hostname → arbitrary text example.com → "v=spf1 include:..." Domain verification, SPF, DKIM, DMARC
SRV service → host + port _http._tcp → 0 5 80 srv.example.com Service discovery (Kubernetes uses this)
PTR IP → hostname 34.216.184.93.in-addr.arpa → api.example.com Reverse DNS lookups (spam filtering, logging)

node:dns — Two APIs, Different Behaviours

Node.js has two distinct DNS APIs with a critical performance difference that most developers don't know about:

dns.lookup() — Uses the OS resolver

import dns from 'node:dns';

// Uses getaddrinfo() — the OS's own resolver
// This is what http.request(), https.request(), fetch() use internally
dns.lookup('api.example.com', (err, address, family) => {
  console.log(address); // '93.184.216.34'
  console.log(family);  // 4 (IPv4) or 6 (IPv6)
});

// Promise-based (dns/promises)
import { lookup } from 'node:dns/promises';

const { address } = await lookup('api.example.com');
console.log(address);
dns.lookup() blocks the thread pool. It calls the OS's synchronous getaddrinfo(), which runs in libuv's thread pool (shared with fs operations). Under high concurrency, this can cause a thread pool bottleneck. It's fine for low-frequency lookups; problematic if you're resolving thousands of hostnames per second.

dns.resolve() — Uses Node's own resolver

import { Resolver } from 'node:dns/promises';

const resolver = new Resolver();
// Optional: use a specific DNS server
resolver.setServers(['8.8.8.8', '1.1.1.1']);

// Resolve A records (IPv4 addresses)
const addresses = await resolver.resolve4('api.example.com');
console.log(addresses); // ['93.184.216.34']

// Resolve MX records
const mxRecords = await resolver.resolveMx('example.com');
// [{ exchange: 'mail.example.com', priority: 10 }]

// Resolve TXT records (for verification)
const txtRecords = await resolver.resolveTxt('example.com');

// Reverse lookup: IP → hostname
const hostnames = await resolver.reverse('93.184.216.34');
dns.resolve() is non-blocking. It sends the DNS query as a UDP datagram (from node:dgram internally) and handles the response asynchronously. It never touches the thread pool. This is better for high-concurrency use cases.

DNS Caching Pitfalls in Node.js

Node.js does not cache DNS results. Unlike browsers, the Node.js DNS resolver does not respect TTLs and cache results. Every call to dns.lookup() or dns.resolve() triggers a fresh OS or network lookup.

This has real consequences:

  • Your app makes 1000 requests to api.stripe.com → potentially 1000 DNS queries
  • In practice, the OS resolver caches, but that's outside Node's control
  • In containers (Docker/Kubernetes), DNS caches may be very short or absent

Solutions: 

// Option 1: Use a caching DNS library
// e.g., 'cacheable-lookup' (used by got, axios v1)
import CacheableLookup from 'cacheable-lookup';
const cacheable = new CacheableLookup();
cacheable.install(http.globalAgent); // patches the http agent

// Option 2: Resolve once on startup and reuse the IP
const { address } = await lookup('db.internal');
// Connect to address directly, skip DNS on every request

// Option 3: Use connection pooling (the agent holds persistent connections)
// This way DNS only runs when a new connection is needed, not per request
