Events — Lesson 02

The Event Loop — 6 Phases

How Node.js handles thousands of concurrent operations on a single thread. The loop that makes non-blocking I/O work.

The Big Picture

Node.js runs your JavaScript on a single thread. But it handles thousands of concurrent connections. How? The event loop — a continuous cycle that checks for completed I/O and runs the appropriate callbacks.

Think of the event loop like a restaurant waiter:

  • There's only one waiter (single thread)
  • Customers place orders (async operations: read file, network request, timer)
  • The waiter gives orders to the kitchen (libuv hands work to OS kernel or thread pool)
  • The waiter doesn't stand and wait — they serve other tables (non-blocking)
  • When food is ready, the kitchen rings a bell (callback queued)
  • The waiter picks it up and delivers it (event loop runs the callback)

The technical model:

  1. Your code starts an async operation (read file, network request, timer)
  2. Node hands it to libuv (C library that manages a thread pool + OS kernel calls)
  3. Your code continues executing (non-blocking)
  4. When the operation completes, libuv queues the callback
  5. The event loop picks up the callback and runs it on the main thread
Frontend analogy: This is exactly how the browser event loop works with setTimeout, fetch, and DOM events. You already understand this model — Node.js just adds more I/O types (files, network, child processes).

The 6 Phases — The Full Picture

The event loop is not one simple queue. It is a cycle of 6 phases, and it goes through them in a fixed order, again and again: 

   ┌───────────────────────────┐
┌─>│      1. timers            │ ← setTimeout, setInterval callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │   2. pending callbacks     │ ← system errors (TCP ECONNREFUSED, etc.)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │   3. idle, prepare         │ ← internal to Node (you never use this)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐       ┌──────────────────┐
│  │      4. poll               │ <──── │ incoming I/O:    │
│  │  (where your server lives) │       │ connections,     │
│  │                            │       │ data, file reads │
│  └─────────────┬─────────────┘       └──────────────────┘
│  ┌─────────────┴─────────────┐
│  │      5. check              │ ← setImmediate callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │   6. close callbacks       │ ← socket.on('close'), server.on('close')
│  └─────────────┬─────────────┘
│                 │
└─────────────────┘ (loop back to timers)

Each phase has its own FIFO queue (first in, first out) of callbacks. When the loop enters a phase, it runs all the callbacks in that phase's queue (or hits a system limit), then moves to the next phase.

Phase 1: Timers

What runs here: Callbacks from setTimeout() and setInterval() whose delay has expired.

Important: the delay you give (e.g., setTimeout(fn, 100)) is a minimum, not an exact time. It means "run this callback after at least 100ms". If the event loop is busy doing other work when 100ms arrives, your callback waits until the loop comes back to the timers phase. 

// "Run this after at least 200ms"
const start = Date.now();

setTimeout(() => {
  // Actual delay might be 203ms, 210ms, etc.
  console.log(`Actual delay: ${Date.now() - start}ms`);
}, 200);
Key insight: Timers don't interrupt other work. They just become "eligible" after their delay. They still have to wait for the event loop to reach the timers phase.

Phase 2: Pending Callbacks

What runs here: System-level I/O error callbacks that were deferred from the previous loop.

For example, if a TCP connection gets ECONNREFUSED, some operating systems wait before reporting this error. That error callback ends up here — not in the poll phase.

You rarely interact with this phase directly. Just know it exists to handle OS-level deferred errors.

Phase 3: Idle / Prepare

What runs here: Internal Node.js housekeeping. You never write code that runs in this phase.

Skip this — it's only for Node.js internals.

Phase 4: Poll (The Most Important Phase)

What runs here: Callbacks for completed I/O operations — file reads, network data, DNS lookups.

This is where your server spends most of its life. When your HTTP server is idle waiting for requests, it is sitting in the poll phase, sleeping, using almost zero CPU.

The poll phase does two things:

  1. Calculate how long to wait — it looks at pending timers and decides "I can sleep for X ms before a timer needs to fire"
  2. Process I/O callbacks — run callbacks for completed I/O, one by one, from the poll queue

The poll phase decision tree:

// When the event loop enters the poll phase:

// 1. Is the poll queue NOT empty?
//    YES → run callbacks until queue is empty or system limit reached

// 2. Is the poll queue empty?
//    → Are there setImmediate() callbacks waiting?
//        YES → leave poll, go to check phase
//        NO  → wait here for new I/O to arrive

// 3. While waiting, are there timers that have expired?
//    YES → leave poll, go back to timers phase

Real example: Timer + File Read

This example from the official Node.js docs shows how the poll phase controls when timers actually fire:

import fs from 'node:fs';

const start = Date.now();

// Schedule a timer for 100ms from now
setTimeout(() => {
  console.log(`Timer fired after ${Date.now() - start}ms`);
}, 100);

// Start a file read (takes ~95ms)
fs.readFile('./package.json', () => {
  // This callback runs in the poll phase
  // Simulate 10ms of work inside the callback
  const cbStart = Date.now();
  while (Date.now() - cbStart < 10) {
    // busy wait (blocking for 10ms)
  }
  console.log(`File callback done after ${Date.now() - start}ms`);
});

What happens step by step:

  1. Event loop starts. Timer is scheduled for 100ms. File read starts (OS handles it).
  2. Event loop enters poll phase. Poll queue is empty (file not done yet). No setImmediate pending.
  3. Poll phase waits. It knows the nearest timer is at 100ms, so it can wait up to 100ms.
  4. At ~95ms, the file read completes. Its callback enters the poll queue.
  5. Poll phase runs the file callback. The callback does 10ms of work (busy loop).
  6. At ~105ms, the callback finishes. Poll queue is now empty.
  7. Event loop checks: any timers expired? YES — the 100ms timer expired at 100ms.
  8. Event loop goes back to timers phase and runs the timer callback.

Result: The timer was scheduled for 100ms but actually fires at ~105ms. The file read callback "held up" the timer by 10ms because the event loop was busy in the poll phase.

This is the key insight: The poll phase controls everything. It decides when to check timers, when to move to the check phase, and when to sleep. Your server literally lives here.

Phase 5: Check

What runs here: setImmediate() callbacks.

This phase exists so you can run code immediately after I/O is done, without waiting for timers. When the poll phase finishes and finds setImmediate callbacks waiting, it moves straight here instead of sleeping. 

import fs from 'node:fs';

fs.readFile('./package.json', () => {
  // Inside an I/O callback (poll phase)
  
  setImmediate(() => {
    console.log('1: setImmediate'); // Runs in check phase (NEXT)
  });
  
  setTimeout(() => {
    console.log('2: setTimeout');  // Runs in timers phase (LATER)
  }, 0);
});

// ALWAYS prints: 1 then 2
// Because: poll → check → ... → timers

Phase 6: Close Callbacks

What runs here: Callbacks for 'close' events when something is destroyed abruptly.

import net from 'node:net';

const socket = net.connect(3000);

socket.on('close', () => {
  // This runs in the close callbacks phase
  console.log('Socket closed');
});

// Force-destroy the socket
socket.destroy();

If a socket or handle is destroyed with .destroy(), the 'close' event fires here. If closed normally (graceful close), it may fire via process.nextTick() instead.

Microtasks: The VIP Queue Between Every Phase

Between every single phase, and even after every single callback, Node.js checks two special queues called microtask queues:

  1. process.nextTick() queue — highest priority. Always drains first.
  2. Promise queue — .then(), .catch(), .finally(), await continuations.

Think of it like this:

// The REAL execution order:
//
//  ┌─ Run current synchronous code ─┐
//  │                                 │
//  └─────────────────────────────────┘
//              │
//              ▼
//  ┌─ Drain nextTick queue ──────────┐  ← ALL nextTick callbacks run
//  └─────────────────────────────────┘
//              │
//              ▼
//  ┌─ Drain Promise queue ───────────┐  ← ALL promise callbacks run
//  └─────────────────────────────────┘
//              │
//              ▼
//  ┌─ Next event loop phase ─────────┐  ← timers / poll / check / etc.
//  └─────────────────────────────────┘
//              │
//              ▼
//  ┌─ Drain nextTick queue (again) ──┐  ← check again after each phase
//  └─────────────────────────────────┘
//              │
//              ▼
//  ┌─ Drain Promise queue (again) ───┐
//  └─────────────────────────────────┘
//              │
//              ▼
//        ... next phase ...

"Drain" means: run ALL the callbacks in that queue until it's empty. Only then move on.

Microtask example — trace the execution

setTimeout(() => console.log('A: timer'), 0);
setImmediate(() => console.log('B: immediate'));
Promise.resolve().then(() => console.log('C: promise'));
process.nextTick(() => console.log('D: nextTick'));
console.log('E: sync');

Let's trace it step by step:

StepWhat happensOutput
1 setTimeout → schedules callback in timers queue (for ≥1ms later) —
2 setImmediate → schedules callback in check queue —
3 Promise.resolve().then() → schedules callback in promise microtask queue —
4 process.nextTick() → schedules callback in nextTick queue —
5 console.log('E: sync') → runs immediately (synchronous) E: sync
6 Synchronous code done. Drain nextTick queue first. D: nextTick
7 Drain promise queue next. C: promise
8 Now enter event loop phases. Timers phase: is 1ms elapsed? Usually yes. A: timer
9 Continue to check phase. B: immediate

Final output:

E: sync
D: nextTick
C: promise
A: timer
B: immediate
The rule is always: sync code → nextTick → promises → event loop phases. Microtasks are "VIP" — they cut the line and run between every single phase.

A deeper microtask example — microtasks inside microtasks

console.log('1: start');

setTimeout(() => {
  console.log('2: timeout');
  
  // A microtask INSIDE a timer callback
  Promise.resolve().then(() => {
    console.log('3: promise inside timeout');
  });
}, 0);

Promise.resolve().then(() => {
  console.log('4: first promise');
  
  // A nextTick INSIDE a promise
  process.nextTick(() => {
    console.log('5: nextTick inside promise');
  });
});

process.nextTick(() => {
  console.log('6: nextTick');
});

console.log('7: end');

Output:

1: start
7: end
6: nextTick
4: first promise
5: nextTick inside promise
2: timeout
3: promise inside timeout

Why this order?

  1. 1: start and 7: end — synchronous, runs first
  2. 6: nextTick — nextTick queue drains (higher priority than promises)
  3. 4: first promise — promise queue drains
  4. 5: nextTick inside promise — the promise callback added a new nextTick. Node drains nextTick again before moving on!
  5. 2: timeout — now the event loop enters the timers phase
  6. 3: promise inside timeout — after the timer callback runs, microtasks drain again before the next phase
⚠️ Key rule: Microtasks can add MORE microtasks. Node.js will keep draining them until BOTH queues are completely empty before moving to the next phase. This means recursive process.nextTick() can starve the event loop forever — I/O callbacks never run.

Complete Code Example — Tracing the Full Loop

Let's write one piece of code that touches every relevant queue, and trace exactly what happens. Copy this to a file and run it with node: 

import fs from 'node:fs';

console.log('1. Sync: script starts');

// Timers phase
setTimeout(() => {
  console.log('6. Timers: setTimeout fires');
}, 0);

// Check phase
setImmediate(() => {
  console.log('7. Check: setImmediate fires');
});

// Poll phase (I/O callback)
fs.readFile('./package.json', () => {
  console.log('8. Poll: file read complete');
  
  // Inside I/O: setImmediate ALWAYS beats setTimeout
  setImmediate(() => console.log('9. Check (inside I/O): setImmediate'));
  setTimeout(() => console.log('10. Timers (inside I/O): setTimeout'), 0);
  
  // Microtasks inside I/O callback
  process.nextTick(() => console.log('11. nextTick inside I/O'));
  Promise.resolve().then(() => console.log('12. Promise inside I/O'));
});

// Microtasks (run before event loop starts)
process.nextTick(() => {
  console.log('4. nextTick: highest microtask priority');
});

Promise.resolve().then(() => {
  console.log('5. Promise: second microtask priority');
});

console.log('2. Sync: script ends');
console.log('3. --- microtasks will run next ---');

Expected output:

1. Sync: script starts
2. Sync: script ends
3. --- microtasks will run next ---
4. nextTick: highest microtask priority
5. Promise: second microtask priority
6. Timers: setTimeout fires
7. Check: setImmediate fires
8. Poll: file read complete
11. nextTick inside I/O
12. Promise inside I/O
9. Check (inside I/O): setImmediate
10. Timers (inside I/O): setTimeout

Reading the output:

  • Lines 1-3: All synchronous code runs first, top to bottom
  • Lines 4-5: Microtasks drain (nextTick first, then promises)
  • Lines 6-7: Event loop phases begin (timers, then check)
  • Line 8: File read completes later, runs in poll phase
  • Lines 11-12: Microtasks inside the I/O callback drain immediately after that callback
  • Lines 9-10: setImmediate fires before setTimeout because inside I/O → check comes before timers

The Poll Phase — Deep Dive

Let's zoom in on the poll phase, because understanding it is understanding how Node.js servers work.

Why does an idle server use 0% CPU?

When your HTTP server has no requests, the event loop reaches the poll phase and asks:

  • Poll queue empty? Yes
  • Any setImmediate scheduled? No
  • Any timers expired? No

So it blocks here. The operating system puts the thread to sleep until new I/O arrives (a new HTTP request, a file read completes, etc.). This is why idle servers use no CPU — the thread is literally sleeping in the kernel.

What wakes it up?

  • A new TCP connection arrives (HTTP request)
  • A file read completes
  • A DNS lookup finishes
  • A timer expires (the poll phase knows the nearest timer deadline and sets a timeout)

Poll phase + timers interaction

The poll phase is smart. Before sleeping, it calculates: "What's the soonest timer deadline?" If there's a setTimeout(fn, 500) pending, the poll phase will sleep for at most 500ms. If I/O arrives before that, it wakes up early. If nothing arrives, it wakes up at 500ms and wraps back to the timers phase. 

// Scenario: server with a health check timer
import http from 'node:http';

// Timer: fire every 10 seconds
setInterval(() => {
  console.log('Health check at', new Date().toISOString());
}, 10_000);

// Server: most time is spent in poll phase waiting for requests
http.createServer((req, res) => {
  // When a request arrives, the poll phase wakes up and runs this
  res.end('OK');
}).listen(3000);

// What happens:
// 1. Event loop enters poll phase
// 2. No requests → sleep (but max 10 seconds because of the timer)
// 3. If a request arrives before 10s → wake up, run request handler
// 4. If 10s passes with no requests → wake up, go to timers, run health check
// 5. Repeat forever

Summary Table

PhaseWhat runs hereReal-world example
1. Timers Expired setTimeout / setInterval Rate limiting resets, session expiry checks
2. Pending Deferred OS error callbacks TCP ECONNREFUSED error reporting
3. Idle/Prepare Internal Node.js work (you never use this)
4. Poll I/O callbacks + waiting for new I/O HTTP requests, file reads, DB responses
5. Check setImmediate() callbacks Run work after I/O without waiting for timers
6. Close 'close' event callbacks Socket destroyed, server shut down

And between every phase:

QueuePriorityExample
process.nextTick() Highest (runs first) Defer emit so listeners can attach
Promise / await Second (runs after nextTick) Async function continuations

Why This Matters for Your Backend

  • Blocking the poll phase = freezing your entire server. One JSON.parse(hugeString) in a request handler means NO other requests are handled until it finishes.
  • Timers are not exact. If you set setTimeout(fn, 100) but the poll phase is busy for 50ms, your timer fires at 150ms.
  • Microtasks always cut the line. await continuations run before any new I/O — this is why async/await feels "fast".
  • Inside I/O, setImmediate always beats setTimeout. This is useful for deferring work to "right after this I/O" without timer overhead.
