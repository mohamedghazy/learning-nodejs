Databases — Lesson 1

SQL vs NoSQL & ACID Fundamentals

Understanding database paradigms and the guarantees that make data trustworthy

Why This Matters

You've built Express APIs that handle HTTP requests. Now those APIs need to store and retrieve data. The database you choose shapes your entire backend architecture: your data model, your query patterns, how you scale, and whether "it's in the database" actually means "it's safe."

Two Paradigms: SQL and NoSQL

Databases fall into two broad families. Understanding the difference isn't about choosing a "winner"—it's about matching the tool to the problem.

SQL (Relational) Databases

SQL databases organize data into tables with predefined schemas. Every row in a table has the same columns. Tables connect to each other through relationships (foreign keys). You query them using SQL (Structured Query Language). 

-- A typical SQL schema: users and orders with a relationship
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  name VARCHAR(100) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INT REFERENCES users(id),
  total DECIMAL(10,2) NOT NULL,
  status VARCHAR(20) DEFAULT 'pending'
);

Key characteristics:

  • Fixed schema — You define the structure upfront. Adding a column requires a migration.
  • Normalized data — Data is split across tables to avoid duplication. A user's name lives in one place.
  • Joins — You combine tables with SQL JOIN operations to reassemble related data.
  • ACID transactions — Operations are reliable and consistent (more on this below).

Examples: PostgreSQL, MySQL, SQLite, SQL Server, Oracle

NoSQL (Non-Relational) Databases

NoSQL is an umbrella term for databases that don't use the relational model. They come in several flavors, each optimized for different access patterns.

Type Structure Use Case Example
Document JSON-like documents Flexible, nested data MongoDB, CouchDB
Key-Value Simple key → value pairs Caching, sessions Redis, DynamoDB
Wide-Column Columns grouped into families Analytics, time-series Cassandra, HBase
Graph Nodes and edges Relationships, social networks Neo4j, Amazon Neptune

A document database like MongoDB stores data as flexible JSON-like documents:

// A MongoDB document — no predefined schema required
{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "email": "alice@example.com",
  "name": "Alice",
  "orders": [
    { "total": 59.99, "status": "completed" },
    { "total": 124.00, "status": "pending" }
  ],
  "preferences": { "newsletter": true }
}

Key characteristics:

  • Flexible/dynamic schema — Each document can have different fields. Easy to evolve.
  • Denormalized data — Related data is often embedded in one document (orders inside user).
  • No joins — You design data to be fetched in one query, not assembled from multiple tables.
  • Horizontal scaling — Designed to distribute across many servers (sharding).

The Core Trade-off

SQL: Structure and Consistency

Choose SQL when your data has clear relationships, you need complex queries across multiple entities, and correctness matters more than raw speed. Think: financial systems, inventory, user accounts.

NoSQL: Flexibility and Scale

Choose NoSQL when your data structure varies, you need to scale horizontally to massive volumes, or your access patterns are simple (fetch one document by ID). Think: real-time feeds, IoT data, caching.

ACID: The Guarantees That Matter

ACID is an acronym for four properties that define reliable database transactions. The term was formalized by Andreas Reuter and Theo Härder in 1983. When a database is "ACID-compliant," it means you can trust it with critical operations.

A — Atomicity

A transaction is all-or-nothing. Either every operation in the transaction succeeds, or none of them take effect. There's no partial state. 

-- Bank transfer: move $100 from Alice to Bob
BEGIN TRANSACTION;

UPDATE accounts SET balance = balance - 100 
WHERE user_id = 'alice';

UPDATE accounts SET balance = balance + 100 
WHERE user_id = 'bob';

COMMIT;
-- If EITHER update fails, BOTH are rolled back
-- Money is never lost or created

Without atomicity: If the system crashes between the two UPDATE statements, Alice loses $100 but Bob never receives it. The money vanishes.

C — Consistency

Every transaction moves the database from one valid state to another. Database constraints (foreign keys, unique indexes, check constraints) are always enforced. A transaction that would violate a constraint is rejected. 

-- Consistency constraint: balance cannot go negative
ALTER TABLE accounts 
ADD CONSTRAINT positive_balance CHECK (balance >= 0);

-- This transaction will FAIL if Alice only has $50
UPDATE accounts SET balance = balance - 100 
WHERE user_id = 'alice';
-- Error: CHECK constraint "positive_balance" violated

I — Isolation

Concurrent transactions don't interfere with each other. Each transaction behaves as if it were the only transaction running. This prevents race conditions.

The Race Condition Problem

Imagine two transactions at month-end: (1) Alice transfers $100 to Bob, and (2) the bank calculates 6% interest on all accounts. If isolation is broken, the interest calculation might read a half-completed state—seeing the $100 credited to Bob but not yet debited from Alice. The bank ends up paying interest on money that was counted twice.

Isolation ensures the interest calculation either sees the state before the transfer or after—never during.
Source: Stanford CS145

D — Durability

Once a transaction is committed, it survives system failures. The data is written to non-volatile storage. Even if the server crashes immediately after commit, the data is safe.

Practical meaning: When your API returns { "status": "success" } after saving to the database, that data is actually saved. A power failure won't lose it.

A user's payment is processed: their card is charged, but the server crashes before the order status is updated to "paid". Which ACID property prevents this inconsistent state?

BASE: The NoSQL Alternative

NoSQL databases often trade ACID guarantees for scalability and availability. Their consistency model is called BASE:

Letter Property What It Means
BA Basically Available The system responds to every request, even during partial failures
S Soft State Data may change over time as it propagates between replicas
E Eventual Consistency All replicas will eventually converge to the same value

Example: You update your profile photo on a social media app. A friend in another region might see your old photo for a few seconds because their request hit a replica that hasn't synced yet. Eventually, all replicas catch up.

ACID vs BASE: Not a Binary Choice

Modern databases blur these lines. MongoDB supports multi-document ACID transactions. PostgreSQL handles JSON natively. Many NoSQL databases let you tune consistency per-query. The models are converging.

The CAP Theorem

The CAP theorem (Eric Brewer, 2000) explains why distributed databases make these trade-offs. A distributed system can only guarantee two of these three properties:

  • Consistency (C) — Every read returns the most recent write
  • Availability (A) — Every request gets a response
  • Partition Tolerance (P) — System works despite network failures between nodes

Network partitions will happen in any distributed system. You can't design them away. That means you must choose: CP (consistency during partitions, some requests fail) or AP (availability during partitions, some reads return stale data).

Choice Database Examples Behavior During Partition
CP MongoDB, HBase, Redis Returns error rather than stale data
AP Cassandra, CouchDB, DynamoDB Returns response, possibly stale

Your app shows a user's follower count. It's okay if the number is a few seconds out of date, but users must always see something. Which CAP trade-off fits this requirement?

When to Use What

Scenario Recommended Why
Financial transactions, payments SQL (PostgreSQL, MySQL) ACID transactions, data integrity is critical
User accounts, authentication SQL (PostgreSQL, MySQL) Relational data, consistency matters
Session storage, caching Redis (Key-Value) Fast reads, simple access pattern
Content management, blogs MongoDB (Document) Flexible schema, nested content
Real-time analytics, logs Cassandra (Wide-Column) High write throughput, time-series
Social graphs, recommendations Neo4j (Graph) Relationship traversal is the core query

Summary

  • SQL databases use tables, schemas, and SQL. They excel at relationships and complex queries.
  • NoSQL databases come in many forms (document, key-value, wide-column, graph). They excel at flexibility and scale.
  • ACID (Atomicity, Consistency, Isolation, Durability) guarantees reliable transactions. SQL databases are ACID-compliant by default.
  • BASE (Basically Available, Soft state, Eventual consistency) trades immediate consistency for availability and scale.
  • CAP theorem explains why distributed databases must choose between consistency and availability during network partitions.
  • Modern databases blur these lines—choose based on your specific requirements, not ideology.
