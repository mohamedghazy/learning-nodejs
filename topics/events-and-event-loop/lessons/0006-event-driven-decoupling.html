Events — Lesson 06

Event-Driven Decoupling

Why decoupled services are easier to extend, test, and replace — and how EventEmitter makes it work in Node.js.

The Problem: Tight Coupling

Imagine an OrderService that, after creating an order, must: send a confirmation email, update analytics, write an audit log, and notify inventory. Here's the naïve approach: 

// order-service.js — tightly coupled
import { sendEmail } from './email-service.js';
import { trackEvent } from './analytics.js';
import { writeAudit } from './audit-log.js';
import { reserveStock } from './inventory.js';

export function createOrder(order) {
  const saved = db.save(order);

  // OrderService "knows" about every downstream consumer
  sendEmail(saved);
  trackEvent('order_created', saved);
  writeAudit('order_created', saved);
  reserveStock(saved);

  return saved;
}

Why this hurts:

  • Adding a new side-effect (e.g., push notifications) means editing OrderService
  • Testing createOrder requires mocking 4 unrelated modules
  • A bug in analytics.js can break order creation
  • The import graph fans out — one file depends on everything

The Solution: Emit, Don't Call

With event-driven decoupling, OrderService only knows about one thing: what happened. It emits a fact. Other modules decide what to do about it: 

// order-service.js — decoupled
import { EventEmitter } from 'node:events';

class OrderService extends EventEmitter {
  createOrder(order) {
    const saved = db.save(order);
    // Just announce what happened — nothing else
    this.emit('order:created', saved);
    return saved;
  }
}

export const orderService = new OrderService();
// email-service.js — subscribes independently
import { orderService } from './order-service.js';
orderService.on('order:created', (order) => {
  sendConfirmation(order.email, order.id);
});

// analytics.js — subscribes independently
import { orderService } from './order-service.js';
orderService.on('order:created', (order) => {
  trackEvent('order_created', { orderId: order.id, total: order.total });
});

Now: adding push notifications means creating a new file and subscribing. OrderService never changes.

Two Patterns: Extend vs. Event Bus

There are two common ways to structure event-driven decoupling in Node.js:

Pattern A: Service extends EventEmitter

Each service is an emitter. Listeners subscribe directly to the service instance. This is what your OrderService code already does. 

// The service IS the emitter
class OrderService extends EventEmitter { /* ... */ }
const orders = new OrderService();
orders.on('order:created', handler);

Good for: domain services with clear ownership. Listeners know which service they care about.

Pattern B: Shared Event Bus

A single EventEmitter instance acts as a central message bus. All services emit and listen through it. 

// event-bus.js
import { EventEmitter } from 'node:events';
export const bus = new EventEmitter();

// order-service.js
import { bus } from './event-bus.js';
bus.emit('order:created', saved);

// email-service.js
import { bus } from './event-bus.js';
bus.on('order:created', handler);

Good for: cross-cutting concerns (logging, metrics) where listeners don't care who emitted.

Tradeoff: A bus can become a "god object" — everything routes through it, making it hard to trace which module emits what. Namespaced event names ('module:action') help.

Real Example: Express Middleware With Events

In a real Express app, you might decouple request handling from side effects. This is directly relevant to your next topic (Express/Fastify): 

// event-bus.js
import { EventEmitter } from 'node:events';
export const appEvents = new EventEmitter();

// routes/orders.js
import { appEvents } from '../event-bus.js';

router.post('/orders', async (req, res) => {
  const order = await Order.create(req.body);
  res.status(201).json(order);

  // Side effects happen AFTER the response
  appEvents.emit('order:created', order);
});

// listeners/notifications.js — loaded at startup
import { appEvents } from '../event-bus.js';
appEvents.on('order:created', async (order) => {
  try {
    await sendPushNotification(order.userId, `Order #${order.id} confirmed`);
  } catch (err) {
    logger.error('Push notification failed', err);
  }
});

The route handler stays focused: validate, save, respond. Everything else is a separate concern. This is a pattern you'll use daily in Express/Fastify backends.

When Decoupling Goes Wrong

Events aren't free. Here are the pitfalls:

PitfallSymptomFix
Invisible control flow You can't "Find All References" to see what happens after emit() Document events. Use a consistent naming convention (domain:action)
Order dependency Listener A must run before Listener B Don't rely on listener order. If order matters, make it explicit with sequential calls
Silent failures Async listener throws, nobody notices Always wrap async listeners in try/catch (see Lesson 3)
Debugging difficulty Stack traces end at emit() Add correlation IDs to event payloads for tracing
Overuse Single subscriber, no extensibility need Just call the function directly. Events add indirection

Decision Framework: When to Decouple With Events

Use this mental model before reaching for emit():

// Ask yourself:

// 1. Are there (or will there be) multiple independent reactions to this action?
//    YES → events make sense

// 2. Should the caller wait for the result of these reactions?
//    YES → don't use events (use async functions)
//    NO  → events are perfect (fire-and-forget side effects)

// 3. Do the reactions need to happen in a specific order?
//    YES → explicit sequential calls are clearer
//    NO  → events work great

// 4. Is this crossing a process/network boundary?
//    YES → use a message queue (Redis Pub/Sub, RabbitMQ)
//    NO  → in-process EventEmitter is fine

Correlation IDs: Making Events Traceable

In production, when an event triggers multiple async side effects, you need to trace them. Add a correlation ID to every event payload: 

import { randomUUID } from 'node:crypto';

class OrderService extends EventEmitter {
  createOrder(order) {
    const correlationId = randomUUID();
    const saved = db.save(order);

    this.emit('order:created', {
      ...saved,
      correlationId,
      timestamp: Date.now()
    });

    return saved;
  }
}

// Every listener logs with the same correlationId
orderService.on('order:created', ({ correlationId, ...order }) => {
  logger.info(`[${correlationId}] Sending email for order ${order.id}`);
});

When something breaks in production, you grep logs by correlationId and see the entire chain of effects from a single event.
