Network Protocols — Lesson 03

UDP and node:dgram

Fire-and-forget packets, broadcasting, and when UDP beats TCP.

The Mental Model: Postal vs Telegram

TCP is like registered mail — the post office confirms every package arrives, will redeliver if lost, and guarantees they arrive in order. UDP is like dropping a message in a public mailbox — it might arrive, might not, might arrive twice, and the post office never tells you what happened.

That sounds terrible. But that "overhead" of TCP (handshakes, ACKs, retransmits, ordering) takes time — and for some applications, getting slightly stale or incomplete data now is far more valuable than getting perfect data in 200ms.

What UDP Guarantees (and What It Doesn't)

PropertyTCPUDP
Delivery guaranteeYes — lost packets are retransmittedNo — lost = gone
Order guaranteeYes — sequence numbers ensure orderNo — packets can arrive out of order
Duplicate preventionYes — deduplication is built inNo — same packet can arrive twice
Connection requiredYes — 3-way handshake firstNo — send directly to any address
Message boundariesNo — TCP is a byte streamYes — each datagram is discrete
Header overhead20–60 bytes per segment8 bytes per datagram
LatencyHigherLower
UDP does preserve message boundaries. Unlike TCP, each UDP send is a self-contained datagram. If you send 3 datagrams, the receiver gets 3 separate messages — never merged. You still need to handle out-of-order or missing datagrams, but framing is not your problem.

The UDP Header (8 bytes)

Compared to TCP's 20–60 byte header, UDP's header is minimal: 

Byte  0-1:  Source Port      (which port the sender used)
Byte  2-3:  Destination Port (which port to deliver to)
Byte  4-5:  Length           (header + data, in bytes)
Byte  6-7:  Checksum         (error detection only, not correction)
Byte  8+:   Data (the payload)

The checksum detects corruption but can't fix it — a corrupted UDP datagram is just dropped. (On IPv4, the checksum is technically optional; on IPv6 it's mandatory.)

node:dgram — The UDP API

UDP Server (Receiver)

import dgram from 'node:dgram';

const server = dgram.createSocket('udp4');
// 'udp4' = IPv4, 'udp6' = IPv6

server.on('message', (msg, rinfo) => {
  // msg is a Buffer (not a string!)
  // rinfo = { address, family, port, size }
  console.log(`Got ${rinfo.size} bytes from ${rinfo.address}:${rinfo.port}`);
  console.log('Message:', msg.toString());

  // Send a reply (create a Buffer)
  const reply = Buffer.from('ACK');
  server.send(reply, rinfo.port, rinfo.address);
});

server.on('error', (err) => {
  console.error('Server error:', err);
  server.close();
});

server.on('listening', () => {
  const { address, port } = server.address();
  console.log(`Listening on ${address}:${port}`);
});

server.bind(41234);

UDP Client (Sender)

import dgram from 'node:dgram';

const client = dgram.createSocket('udp4');

const message = Buffer.from('Hello, server!');

// send(msg, offset, length, port, address, callback)
client.send(message, 0, message.length, 41234, '127.0.0.1', (err) => {
  if (err) console.error('Send failed:', err);
  // NOTE: No error here means the OS accepted the datagram.
  // It does NOT mean the server received it!
  client.close();  // Close after sending (UDP is connectionless)
});
The callback does not mean delivery. The callback fires when the OS has accepted the datagram for sending. The datagram might still be lost in the network. There's no confirmation that the server received it.

Broadcasting and Multicasting

One major advantage UDP has over TCP: you can send one datagram to multiple recipients without multiple sends. TCP is always unicast (one-to-one).

Broadcast — "All devices on this subnet, listen up"

const client = dgram.createSocket('udp4');

// Must enable broadcast explicitly
client.setBroadcast(true);

const msg = Buffer.from('Service announcement: I am online at port 8080');

// 255.255.255.255 = limited broadcast (all hosts on local network)
client.send(msg, 0, msg.length, 41234, '255.255.255.255');

Use case: Service discovery on a local network (e.g., a printer announcing itself, mDNS/.local domain resolution, IoT device discovery).

Multicast — "Subscribers to this channel, listen up"

const server = dgram.createSocket('udp4');
server.bind(41234, () => {
  // Join a multicast group — 224.0.0.0/4 is reserved for multicast
  server.addMembership('224.1.1.1');
});

server.on('message', (msg) => {
  console.log('Multicast message:', msg.toString());
});

Use case: Live video streaming to multiple viewers, stock ticker feeds, multiplayer game world state synchronization.

Real-World UDP Use Cases

DNS — The Most Common UDP You Use Every Day

Every DNS query is a UDP datagram (usually). Your browser sends a 30-byte query to port 53 and expects a response within ~100ms. If it doesn't arrive, it retries — the application handles reliability, not the protocol. Large DNS responses fall back to TCP.

Video Streaming (WebRTC, RTP)

A video frame arrives 33ms late? Show it late or drop it. A TCP retransmit at the wrong moment would freeze the entire video. UDP lets the application decide what to do with late/missing frames.

Online Gaming

Your character's position 100ms ago is useless — you need the current position now. Games use UDP with their own application-layer protocol for delta compression (send only what changed) and client-side prediction (interpolate between known positions).

QUIC (HTTP/3's Transport)

QUIC is Google's protocol (now an IETF standard) that implements TCP-like reliability, multiplexing, and TLS — all on top of UDP. Why? To avoid TCP's head-of-line blocking and to make connection migration work (switching from Wi-Fi to LTE without dropping the connection).

HTTP/3 runs over QUIC, which runs over UDP. The future of HTTP is UDP underneath, with reliability built in the application layer. This gives fine-grained control over what to retransmit, rather than blocking all streams.

Practical: UDP Log Aggregator

A common production pattern: services emit log events over UDP to a central aggregator. If the aggregator is temporarily down, log events are dropped — which is acceptable for non-critical logs. This avoids the situation where a slow log sink causes your API to slow down. 

// logger.js — in each service
import dgram from 'node:dgram';

const sock = dgram.createSocket('udp4');

export function logEvent(level, msg, meta = {}) {
  const payload = Buffer.from(JSON.stringify({
    ts: Date.now(),
    level,
    msg,
    ...meta
  }));
  // Fire-and-forget: if it fails, we don't care — it's just a log
  sock.send(payload, 9999, 'log-aggregator.internal');
}

// aggregator.js — central log server
import dgram from 'node:dgram';

const aggregator = dgram.createSocket('udp4');

aggregator.on('message', (msg) => {
  try {
    const entry = JSON.parse(msg.toString());
    // Write to database, file, or forward to ELK/Datadog
    console.log(entry);
  } catch {
    // Corrupted datagram — just drop it
  }
});

aggregator.bind(9999);
