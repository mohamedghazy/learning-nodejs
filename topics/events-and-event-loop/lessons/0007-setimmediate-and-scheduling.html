Events — Lesson 07

setImmediate, setTimeout & setInterval

Three scheduling APIs, three different behaviors. Why setImmediate is essential for EventEmitter patterns.

The Three Scheduling APIs

Node.js gives you three ways to schedule code to run "later":

APIWhat it doesEvent loop phase
setTimeout(fn, ms) Run fn once, after at least ms milliseconds Timers phase
setInterval(fn, ms) Run fn repeatedly, every ms milliseconds Timers phase
setImmediate(fn) Run fn once, as soon as the current I/O cycle completes Check phase

They live in different event loop phases. Recall from Lesson 2: 

// Event loop phase order:
// timers → pending → idle → poll → check → close
//   ↑ setTimeout/setInterval          ↑ setImmediate

setTimeout vs setImmediate: The Subtle Difference

setTimeout(fn, 0) and setImmediate(fn) seem identical — "run this ASAP." But their behavior depends on where you call them from:

Called from the main module (top-level)

// Order is NON-DETERMINISTIC at top level
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

// Could print either order! Depends on system timer resolution.
// Sometimes: timeout → immediate
// Sometimes: immediate → timeout

Why? setTimeout(fn, 0) actually means "after at least 1ms" (minimum timer granularity). If the event loop starts fast enough, it enters the timers phase before 1ms has elapsed, finds nothing, moves to poll, then check (runs setImmediate). But if system load causes a tiny delay, the timer may already be expired.

Called inside an I/O callback

import { readFile } from 'node:fs';

readFile('./package.json', () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});

// ALWAYS prints:
// immediate
// timeout

Inside an I/O callback, you're in the poll phase. The next phase is check (where setImmediate lives). The timers phase comes around on the next iteration. So setImmediate always fires first here.

Rule of thumb: Inside I/O callbacks, setImmediate always beats setTimeout(fn, 0). At top-level, order is unpredictable. This is documented in the official Node.js setImmediate guide.

Why setImmediate Matters for EventEmitter

Here's the critical EventEmitter problem that setImmediate solves: emitting an event before listeners are attached.

The broken pattern

import { EventEmitter } from 'node:events';

class DataLoader extends EventEmitter {
  constructor(url) {
    super();
    // ❌ BUG: emitting in the constructor
    this.emit('ready', { url });
  }
}

// The listener is attached AFTER the constructor runs
const loader = new DataLoader('https://api.example.com');
loader.on('ready', (data) => {
  console.log('Ready!', data); // ← NEVER fires!
});

The emit happens synchronously inside the constructor. At that point, loader.on('ready', ...) hasn't been called yet — the constructor must return before you can add listeners to the instance.

The fix: defer with setImmediate

class DataLoader extends EventEmitter {
  constructor(url) {
    super();
    // ✅ Defer the emit to the check phase
    setImmediate(() => {
      this.emit('ready', { url });
    });
  }
}

const loader = new DataLoader('https://api.example.com');
loader.on('ready', (data) => {
  console.log('Ready!', data); // ✅ NOW it fires
});

setImmediate pushes the emit to the check phase — after all synchronous code in the current execution finishes. By then, .on('ready', ...) has already been registered.

This is a real Node.js core pattern. The net.Server class uses this exact technique — it defers certain events so you have time to attach listeners after calling the constructor. You'll see this everywhere in Node.js source code.

Why Not process.nextTick Instead?

You could use process.nextTick for the same purpose — it also defers execution past the current synchronous code. But there's an important difference:

setImmediateprocess.nextTick
Runs in Check phase (macrotask) Between phases (microtask)
I/O starvation risk No — I/O callbacks run first (poll phase) Yes — recursive nextTick blocks I/O forever
Use case Yield to the event loop, let I/O flow Run before any I/O (rare, careful use) 
// ❌ Dangerous: recursive nextTick starves I/O
function recurse() {
  process.nextTick(recurse); // I/O callbacks never run!
}

// ✅ Safe: recursive setImmediate yields to I/O each iteration
function recurse() {
  setImmediate(recurse); // I/O callbacks run between iterations
}

For the constructor pattern, both work. But setImmediate is the safer default because it won't starve I/O if something unexpected happens.

setInterval: The Repeating Timer

setInterval is simply setTimeout that re-schedules itself: 

// Runs handler every 5 seconds
const intervalId = setInterval(() => {
  console.log('Health check at', new Date().toISOString());
}, 5000);

// Stop it later
clearInterval(intervalId);

Key behaviors:

  • If a callback takes longer than the interval, calls will stack up — never overlap (they wait), but drift accumulates
  • Like setTimeout, the delay is a minimum — if the event loop is busy, it fires late
  • An uncancelled interval keeps the process alive forever (useful for servers, annoying in scripts)

setInterval vs recursive setTimeout

// setInterval: fixed delay BETWEEN START of each call
// If handler takes 200ms, next call is only 800ms after handler finishes (for 1000ms interval)
setInterval(handler, 1000);

// recursive setTimeout: fixed delay AFTER END of each call
// Always exactly 1000ms of rest between calls, regardless of handler duration
function loop() {
  handler();
  setTimeout(loop, 1000);
}
loop();

For production health checks, polling, or retry logic: prefer recursive setTimeout so a slow handler doesn't cause drift.

Practical Summary: Which to Use When

ScenarioUseWhy
Defer emit in constructor setImmediate Lets listeners attach first, doesn't block I/O
Chunk CPU-heavy work setImmediate Yields to I/O between chunks (Lesson 4)
Delay something by N ms setTimeout Timer-based scheduling with minimum delay
Repeat something every N ms setInterval or recursive setTimeout Periodic tasks (prefer recursive setTimeout for precision)
Run before any pending I/O process.nextTick Rare — use when you must run before the loop continues

Try It: The Constructor Problem

Run this in your code/ directory to see the bug and the fix:

// scheduling-test.js
import { EventEmitter } from 'node:events';

// ❌ Broken: emit in constructor
class BrokenLoader extends EventEmitter {
  constructor() {
    super();
    this.emit('ready', 'data loaded');
  }
}

const broken = new BrokenLoader();
broken.on('ready', (msg) => console.log('Broken heard:', msg));
// Nothing prints!

// ✅ Fixed: defer with setImmediate
class FixedLoader extends EventEmitter {
  constructor() {
    super();
    setImmediate(() => this.emit('ready', 'data loaded'));
  }
}

const fixed = new FixedLoader();
fixed.on('ready', (msg) => console.log('Fixed heard:', msg));
// Prints: Fixed heard: data loaded
